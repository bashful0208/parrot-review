# Admin Overview 后台页设计

> 目标：为 `reviewer` 设计一个带左侧 `sidebar` 的后台管理框架，默认落地到 `Overview` 首页，并兼容桌面端可折叠侧栏与移动端抽屉导航。

## 背景判断

根据当前项目前端现状，登录后首页已经具备明显的 dashboard 基础能力：

- 已有登录态校验与登录后首页入口
- 首页已经展示 `Hero`、KPI、`Recent Review Runs`、`Repository Health`、`Risk Insights`
- 当前产品更像“AI Code Review 运营工作台”，而不是内容管理系统或纯设置面板

因此，最适合的后台方向不是纯内容管理型，也不是纯系统配置型，而是：

- 整体上采用混合型后台框架
- 默认首页优先做“数据总览型后台”
- 通过左侧 `sidebar` 承载后续扩展到仓库、运行记录、规则、团队、设置等页面

## 设计目标

这次设计需要同时解决四件事：

1. 让当前首页从单页 dashboard 升级为完整后台框架
2. 让用户在登录后第一屏快速理解组织当前审查状态
3. 让后续模块页有统一的导航骨架和布局约束
4. 让现有 dashboard 模块可以低成本迁入新的后台壳子

页面定位为：`Operator Console`。

## 适用用户与使用场景

- 默认用户：登录后的组织成员
- 默认入口：系统登录后的第一屏
- 当前优先页面：`Overview`
- 未来扩展页面：`Repositories`、`Review Runs`、`Policies`、`Team`、`Settings`

该后台的重点不是“录入大量内容”，而是：

- 查看组织级审查运行状态
- 续接最近 review 工作
- 发现风险与异常仓库
- 进入后续管理模块

## 总体方案

推荐采用：`运营控制台` 方案。

理由：

- 最贴合当前项目已经存在的 dashboard 数据结构
- 能自然承接现在首页已有模块
- 后续扩展菜单页时不需要推翻整体信息架构
- 既能满足总览，也能承载管理型页面

## 信息架构

后台采用两层结构：

1. 外层 `Admin Shell`
2. 内层具体页面（当前为 `Overview`）

### 1. 外层 `Admin Shell`

负责：

- 左侧 `sidebar`
- 顶部工具栏
- 页面内容容器
- 桌面/移动端导航切换

### 2. 内层页面层

当前只实现 `Overview`，后续页面沿用同一骨架。

建议一级导航如下：

- `Overview`
- `Repositories`
- `Review Runs`
- `Policies`
- `Team`
- `Settings`

其中：

- `Overview` 为默认激活项
- `Settings` 与 `Log out` 视觉上应与主业务导航分区
- 未来允许在 `Repositories` / `Review Runs` 下扩展二级页，但本次不设计二级导航

## Sidebar 设计

### 目标

`sidebar` 不只是菜单容器，而是后台骨架的稳定锚点。

它需要做到：

- 在桌面端提供持续可见的导航定位
- 在移动端不挤压内容区
- 在折叠状态下仍能保留可识别的导航能力

### 结构

`sidebar` 分为三段：

1. 顶部品牌区
2. 中部主导航区
3. 底部用户区

#### 顶部品牌区

内容：

- 产品名 / logo 区
- 当前 workspace / organization 名称

要求：

- 展开态显示完整名称
- 折叠态至少保留 logo / 首字母标识
- 品牌区应明显区别于普通导航项

#### 中部主导航区

内容：

- `Overview`
- `Repositories`
- `Review Runs`
- `Policies`
- `Team`
- `Settings`

要求：

- 每项都使用图标 + 文本
- 当前激活项必须有明显激活态
- 折叠态优先保留图标，并通过 tooltip 或 title 提供语义补充
- 禁止只靠颜色区分激活项，应同时使用背景、字重或侧边指示条

#### 底部用户区

内容：

- 用户头像
- 用户名 / 邮箱
- workspace 切换入口（如当前阶段没有真实多 workspace，可先保留视觉位）
- `Log out`

要求：

- 危险或退出类动作与普通导航分开
- 用户信息区在折叠态可简化为头像按钮

### 行为模式

本次采用“双态自适应”方案：

- 桌面端：可展开 / 收起
- 移动端：抽屉式 `Sheet`

#### 桌面端

- 默认展开
- 用户可手动收起为窄栏
- 收起后内容区自动扩展
- 折叠按钮位置应稳定且容易发现

#### 移动端

- 默认隐藏 `sidebar`
- 通过顶部菜单按钮唤起左侧抽屉
- 抽屉打开后覆盖内容区，不与正文并排
- 关闭方式支持点击遮罩或显式关闭按钮

## Overview 页面设计

`Overview` 是后台默认首页，负责同时承载总览、续接与风险判断。

### 页面结构

建议分为四个区域：

1. 顶栏
2. KPI 总览区
3. 主内容双栏区
4. 风险 / 快捷动作补充区

### 1. 顶栏

左侧内容：

- 页面标题：`Overview`
- 一句状态摘要，例如当前组织运行态说明

右侧内容：

- 全局搜索
- 时间范围筛选
- 主操作按钮：`New Review`

要求：

- 顶栏应偏工具条而不是营销 Hero
- 搜索与筛选优先服务后台操作，不做复杂装饰
- 主操作按钮在桌面与移动端都要可见

### 2. KPI 总览区

推荐 4 个卡片：

- `Active Repositories`
- `Review Runs`
- `Open Findings`
- `Success Rate`

要求：

- KPI 数字清晰突出，但不走大屏风格
- 卡片之间层级一致，避免某个指标无意义抢眼
- 次级说明可显示环比、状态说明或变化趋势

### 3. 主内容双栏区

#### 左侧：`Recent Review Runs`

作用：

- 展示最近 review 工作流
- 作为首页最关键业务模块之一

每条记录至少显示：

- repository 名称
- PR 标题或编号
- 当前状态
- 触发时间
- 风险摘要

要求：

- 左侧内容面积应大于右侧
- 行项目可点击，后续进入运行详情
- 状态信息不能只用颜色表达

#### 右侧：`Repository Health`

作用：

- 呈现组织下最值得关注的仓库资产

每项至少显示：

- repository 名称
- 最近一次 review 状态或时间
- findings 数量
- 健康度摘要

要求：

- 偏紧凑列表，而不是重表格
- 强调优先级与可读性
- 每项允许有轻量状态标签

### 4. 风险 / 快捷动作补充区

#### `Risk Insights`

作用：

- 从任务结果上升到组织级风险判断

内容建议：

- 风险等级分布
- 近期异常趋势
- 重点受影响仓库或规则

要求：

- 即使使用占位数据，也要按真实后台信息块设计
- 不做成装饰性图表，应强调结论和风险信号

#### `Quick Actions`

建议动作：

- `New Review`
- `Connect Repository`
- `View All Runs`

要求：

- 使用可点击卡片或高识别按钮组
- 视觉优先级低于 KPI，但高于普通辅助信息
- 在移动端应保持容易点击

## 视觉风格

整体风格采用：`冷静、可信、轻技术感`。

### 视觉原则

- 延续当前项目已有的浅蓝灰、轻渐变方向
- 收敛 marketing 气质，增强后台感与信息稳定性
- 通过边框、背景层次、留白与比例建立秩序感
- 避免 BI 大屏式夸张视觉和过强发光效果

### 布局层次

- `sidebar` 使用更深一层的中性色背景，与内容区形成结构分割
- 主内容区使用浅色背景与高可读卡片
- 顶栏可以轻透明，但不能影响工具可读性
- 卡片圆角、边框、阴影需统一

### 颜色策略

- 主色：蓝系 / cyan 系，用于主品牌和主操作
- 中性色：`slate/zinc` 系，用于背景、边框、正文
- 成功：绿色
- 风险：橙色
- 严重失败：红色

要求：

- 状态色仅用于状态表达，不做大面积背景主色
- 页面整体保持克制，避免“整页都是高饱和标签”

### 排版策略

- 标题更紧凑、更有秩序感
- 正文与说明文字中性、稳定、便于扫读
- KPI 数字要突出，但不要破坏整体节奏
- 次级信息统一降低一个层级，不要灰得发虚

## 组件策略

根据项目约定，本次 UI 默认优先使用 `shadcn/ui` 组件能力。

推荐映射：

- 后台骨架导航：`Sidebar`
- 卡片容器：`Card`
- 操作按钮：`Button`
- 搜索框：`Input`
- 筛选器：`Select`
- 用户菜单：`DropdownMenu`
- 用户信息：`Avatar`
- 状态标签：`Badge`
- 移动端抽屉导航：`Sheet`

策略要求：

- 优先组合 `shadcn/ui` 现有组件，不单独发明一套后台基础组件形态
- 允许在业务层做轻封装，但不破坏原有无障碍结构
- 所有样式调整优先通过 `className`、`cn()`、Tailwind utility classes 完成

## 响应式策略

### Desktop

- 使用左侧固定 `sidebar` + 右侧内容区
- `Overview` 主体保持双栏布局
- KPI 采用 4 列或 2x2 网格

### Tablet

- `sidebar` 允许收起
- 主内容区可切为更紧凑的双列或局部单列
- 顶栏搜索与筛选允许换行

### Mobile

- `sidebar` 切换为左侧抽屉
- 所有模块改单列堆叠
- 模块顺序保持：
  - `Overview` 顶栏
  - KPI
  - `Recent Review Runs`
  - `Repository Health`
  - `Risk Insights`
  - `Quick Actions`

要求：

- 不允许出现横向滚动
- 主操作保持明显可见
- 抽屉导航和内容滚动互不干扰

## 数据策略

当前实现应采用“真实数据优先 + 增强区允许占位”的策略。

### 优先真实化的数据

- 当前登录用户
- 当前 organization / workspace 名称
- 基础 KPI 数量
- 最近 review runs
- 仓库健康列表的基础状态

### 允许先占位的数据

- 趋势图
- 风险分布图
- 高级评分
- 异常波动分析

这样可以优先交付完整后台结构，而不把实现范围扩到完整分析系统。

## 组件拆分建议

建议拆为以下职责边界：

- `AdminShell`：后台总容器，组织 `sidebar`、顶栏与内容区
- `AdminSidebar`：负责导航、品牌区、用户区
- `AdminTopbar`：负责搜索、筛选、主操作
- `OverviewKpiGrid`：负责 KPI
- `OverviewRecentRunsCard`：负责最近运行列表
- `OverviewRepositoryHealthCard`：负责仓库健康列表
- `OverviewRiskInsightsCard`：负责风险洞察
- `OverviewQuickActionsCard`：负责快捷动作

原则：

- 骨架与业务模块分离
- 每个组件只负责一个展示职责
- 尽量避免继续把所有布局堆回首页单文件

## 空状态与异常策略

### 空状态

- 没有仓库时：引导 `Connect Repository`
- 没有 review runs 时：引导 `New Review`
- 没有增强型洞察数据时：显示自然占位态，不留空洞

### 异常策略

- 某一模块数据异常时，允许模块级降级
- 不因为单块失败导致整页不可用
- 保持项目现有日志与错误处理规范
- 不使用 `console.log` / `console.error`

## 范围边界

本次设计只覆盖：

- 带左侧 `sidebar` 的后台框架
- 默认 `Overview` 首页的信息架构与视觉方向
- 桌面/移动端导航行为

本次不覆盖：

- `Repositories`、`Review Runs`、`Policies`、`Team`、`Settings` 的具体详情页设计
- review run 详情页
- 完整图表分析系统
- 全部统计指标的一次性真实化

## 验收标准

当该设计被实现后，应满足：

- 登录后首页从单页 dashboard 升级为后台管理框架
- 左侧 `sidebar` 在桌面端可折叠、移动端可抽屉打开
- `Overview` 首页具备总览、续接、洞察、快捷入口四类价值
- 现有 dashboard 模块可自然迁入新骨架
- UI 风格明显更像专业后台，而不是 marketing 页面
- 实现默认优先使用 `shadcn/ui` 组件能力
