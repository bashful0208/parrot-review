# P0 开发进度跟踪调整设计

> 目标：在现有 `p0-development-progress.md` 基础上继续细化执行粒度，并将数据库底座明确前移到 `Phase 0`；当前数据库目标口径为自建 `PostgreSQL`，其它平台能力保持中性待定。

## 调整结论

- 保持“阶段 + 能力域”主结构不变
- 将“数据库底座”从分散依赖关系中抽离，前移到 `Phase 0`
- 在 `Phase 0` 新增 `0.4 PostgreSQL 数据底座与平台接口预留`
- `Phase 1` 保持“业务数据模型与权限隔离”定位，不再承载数据库底座职责
- 继续细化优先覆盖 `Phase 0 ~ Phase 3`，因为这些阶段决定最早可执行顺序

## 为什么要把 PostgreSQL 数据底座前移到 Phase 0

当前 P0 的关键链路首先依赖数据库底座与最小平台边界明确：

- `PostgreSQL` 承担核心业务数据存储
- 登录 / 认证能力需要先定义边界，但暂不锁定具体产品
- 状态同步能力需要先定义边界，但暂不锁定具体产品
- secret 管理能力需要先定义边界，但暂不锁定具体产品
- 文件存储虽非最早主路径核心，但同样属于后续平台能力的一部分

如果仍把这些前置条件散落在后续阶段，会导致执行顺序不清晰：

- 先做业务表，但数据库运行与迁移基线未明确
- 先做登录和组织体验，但认证边界未明确
- 先做状态更新，但状态同步能力边界未前置
- 先做模型配置，但 secret 管理能力未被当作基础能力处理

因此，更适合作为 `Phase 0` 前置项的是“自建 `PostgreSQL` 数据底座 + 其它平台能力接口预留”，而不是把某个具体平台产品当前置既定方案。

## `0.4 PostgreSQL 数据底座与平台接口预留` 范围

### `PostgreSQL`

- 明确项目使用的自建 `PostgreSQL` 实例与环境边界
- 明确迁移执行方式与环境边界
- 明确连接配置与 server-side 使用约束
- 明确数据库角色边界和敏感操作原则

### `Auth`

- 明确登录方式与会话模型的能力边界
- 明确用户与组织上下文关联方式
- 明确服务端读取当前用户身份的边界
- 明确前端可见与不可见的认证信息边界
- 不锁定具体供应商或产品

### `Storage`

- 明确是否作为 P0 必需能力启用
- 如果启用，明确存储命名与访问边界
- 如果当前阶段暂不进入主链路，保留为平台接口预留
- 不锁定具体供应商或产品

### `Realtime`

- 明确 `review_run` 状态同步能力边界
- 明确订阅对象与组织隔离原则
- 明确只推送必要状态，不扩大广播范围
- 可交付轮询或其它最小可工作机制之一，但不锁定具体供应商或产品

### `Secrets`

- 明确 provider 密钥能力边界与最小可工作实现
- 明确业务表只存 `vault_secret_id` 等 secret reference 与元数据；这些字段名仅表示历史命名或通用 secret reference 语义，不代表 Vault 方案已定
- 明确前端禁止读取原始密钥
- 明确 worker 在服务端按组织 / 仓库解析 secret reference
- 不锁定具体供应商或产品

## 文档细化策略

### 细化重点

优先继续细化：

- `Phase 0`
- `Phase 1`
- `Phase 2`
- `Phase 3`

原因：这些阶段直接决定是否能形成最小可运行闭环。

### 细化粒度原则

每个事项尽量拆成以下类型之一：

- 建表 / 字段 / 索引 / 约束
- provider / handler / consumer / service
- 状态流转
- 幂等 / 重试 / 超时 / 失败路径
- 页面行为 / 展示项 / 配置动作
- 最小验收动作

### 不做的调整

- 不把整份文档改造成 implementation plan
- 不给每项补具体命令和代码块
- 不大幅重排 `Phase 4 ~ Phase 7` 的主结构，只做必要细化

## 结果预期

调整完成后，进度表会更清楚回答 3 个问题：

1. 什么必须先做，什么可以后做
2. 数据库底座在整条链路里属于前置基础，而不是后置功能模块
3. 当前文档是否足够支持按阶段持续推进与勾选跟踪
