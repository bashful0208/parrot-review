# P0 开发进度跟踪调整设计

> 目标：在现有 `p0-development-progress.md` 基础上继续细化执行粒度，并将 `Supabase` 明确前移到 `Phase 0` 作为平台底座。

## 调整结论

- 保持“阶段 + 能力域”主结构不变
- 将 `Supabase` 从分散依赖关系中抽离，前移到 `Phase 0`
- 在 `Phase 0` 新增 `0.4 Supabase 平台底座`
- `Phase 1` 保持“业务数据模型与权限隔离”定位，不再承载平台底座职责
- 继续细化优先覆盖 `Phase 0 ~ Phase 3`，因为这些阶段决定最早可执行顺序

## 为什么要把 Supabase 前移到 Phase 0

当前 P0 的关键链路大量依赖 `Supabase`：

- `Postgres` 承担核心业务数据存储
- `Auth` 承担登录与组织上下文
- `Realtime` 承担审查状态推送
- `Vault` 承担模型密钥安全存储
- `Storage` 虽非最早主路径核心，但属于统一平台能力的一部分

如果仍把这些前置条件散落在后续阶段，会导致执行顺序不清晰：

- 先做业务表，但数据库运行与迁移基线未明确
- 先做登录和组织体验，但认证边界未明确
- 先做实时状态更新，但 `Realtime` 依赖未前置
- 先做模型配置，但密钥托管能力未被当作基础能力处理

因此，`Supabase` 更适合作为 `Phase 0` 的平台底座，而不是后置的功能配套项。

## 调整后的阶段结构

1. `Phase 0 基础底座`
   - `0.1 Monorepo 与工程规范`
   - `0.2 环境变量与配置约束`
   - `0.3 日志、错误与运行约束`
   - `0.4 Supabase 平台底座`
2. `Phase 1 多租户与核心数据模型`
3. `Phase 2 仓库接入链路`
4. `Phase 3 异步审查执行链路`
5. `Phase 4 AI 与审查结果系统`
6. `Phase 5 控制台交付闭环`
7. `Phase 6 P0 增强能力`
8. `Phase 7 测试、观测与验收`

## `0.4 Supabase 平台底座` 范围

### `Postgres`

- 明确项目使用的 `Supabase Postgres` 实例
- 明确迁移执行方式与环境边界
- 明确连接配置与 server-side 使用约束
- 明确数据库角色边界和敏感操作原则

### `Auth`

- 明确登录方式与会话模型
- 明确用户与组织上下文关联方式
- 明确服务端读取当前用户身份的边界
- 明确前端可见与不可见的认证信息边界

### `Storage`

- 明确是否作为 P0 必需能力启用
- 如果启用，明确 bucket 命名与访问边界
- 如果当前阶段暂不进入主链路，保留为平台预置能力

### `Realtime`

- 明确 `review_run` 状态推送依赖 `Supabase Realtime`
- 明确订阅对象与组织隔离原则
- 明确只推送必要状态，不扩大广播范围

### `Vault`

- 明确 provider 密钥使用 `Supabase Vault`
- 明确业务表只存 `vault_secret_id` 与元数据
- 明确前端禁止读取原始密钥
- 明确 worker 在服务端按组织 / 仓库解析密钥

## 文档细化策略

### 细化重点

优先继续细化：

- `Phase 0`
- `Phase 1`
- `Phase 2`
- `Phase 3`

原因：这些阶段直接决定是否能形成最小可运行闭环。

### 细化粒度原则

每个事项尽量拆成以下类型之一：

- 建表 / 字段 / 索引 / 约束
- provider / handler / consumer / service
- 状态流转
- 幂等 / 重试 / 超时 / 失败路径
- 页面行为 / 展示项 / 配置动作
- 最小验收动作

### 不做的调整

- 不把整份文档改造成 implementation plan
- 不给每项补具体命令和代码块
- 不大幅重排 `Phase 4 ~ Phase 7` 的主结构，只做必要细化

## 结果预期

调整完成后，进度表会更清楚回答 3 个问题：

1. 什么必须先做，什么可以后做
2. `Supabase` 在整条链路里属于平台底座还是功能模块
3. 当前文档是否足够支持按阶段持续推进与勾选跟踪
