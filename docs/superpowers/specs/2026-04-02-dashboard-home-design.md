# Dashboard 首页设计

> 目标：为 `reviewer` 的登录后首页设计一个组织级 `dashboard`，在当前阶段优先完成高保真产品结构与视觉框架，不要求一次性接齐全部真实数据。

## 背景判断

根据当前项目状态，`reviewer` 不是营销站点，而是一个围绕 AI Code Review 的工作台产品，现有主线包括：

- 登录与会话能力已具备，首页当前为登录后落地页
- 核心业务对象已明确：`organization`、`repository`、`pull_request`、`review_run`、`review_issue`
- 项目主方向是多租户组织隔离、仓库接入、PR 审查运行与审查结果闭环
- 当前更适合先做“登录后 dashboard 首页”，而不是继续扩展简单欢迎页

因此，本次首页应服务于“组织级审查运营 + 工作入口 + 风险结果浏览”三类需求。

## 设计目标

首页需要同时完成三件事：

1. 让用户快速理解当前组织的审查健康度
2. 让用户能从首页直接进入关键操作
3. 让用户能继续最近的 review 工作并看到主要风险信号

页面定位为：`Executive Workspace`。

它不是纯数据墙，也不是只放快捷按钮，而是兼顾品牌感、总览感与可执行性的混合型 dashboard。

## 用户与上下文

- 默认查看范围：当前组织级
- 页面使用场景：用户登录后进入系统的第一屏
- 当前阶段优先级：结构优先，高保真产品壳子优先，允许增强模块先使用占位数据
- 视觉方向：高级产品感，现代 SaaS 气质，保留工程产品可信度

## 信息架构

页面采用三段式结构：

1. `Hero + KPI` 总览区
2. `Quick Actions + Recent Review Runs` 工作区
3. `Risk Insights + Repository Health` 洞察区

信息层级原则：

- 第一屏先给组织状态和核心指标
- 中间提供明确可操作入口
- 下方承接风险洞察和仓库级健康信息
- 桌面端强调主次层级，移动端保持同样顺序的单列堆叠

## 页面模块设计

### 1. Hero 总览区

作用：建立当前组织上下文，并给出进入系统后的第一判断。

内容包括：

- 当前组织名称
- 欢迎语或简短概括文案
- 当前组织状态摘要
- 3 到 4 个核心 KPI

建议 KPI：

- `Active Repositories`
- `Reviews This Week`
- `Open Findings`
- `Success Rate`

设计要求：

- 不做普通均质卡片堆叠，要有明显主视觉和层次
- 视觉上体现“组织审查指挥台”感受
- Hero 区是品牌感最强的一层，但仍然服务于数据阅读

### 2. Quick Actions 快速动作区

作用：让首页不只是看板，也成为工作入口。

首批动作固定为：

- `New Review`
- `Connect Repository`
- `View All Runs`

设计要求：

- 使用 action card，而不只是简单按钮
- 每张卡片都要包含动作标题、简短说明、可点击反馈
- 在视觉优先级上低于 Hero，但高于普通数据列表

### 3. Recent Review Runs 最近审查区

作用：承接用户的连续工作流，是首页最关键的业务模块。

每条记录至少显示：

- repository 名称
- PR 标题或编号
- 当前状态
- 触发时间
- 风险等级摘要

设计要求：

- 作为首页主内容卡之一，面积应明显大于次级模块
- 用户点击任一条记录时，应自然进入对应详情页或运行详情
- 状态信息必须可快速扫读，避免只靠颜色表达

### 4. Risk Insights 风险洞察区

作用：把 review 结果从“任务列表”提升到“组织洞察”。

建议拆成两个相邻子模块：

- findings 分布：`Critical / High / Medium / Low`
- 趋势或重点影响对象：例如 `Most affected repositories` 或近期问题趋势

当前阶段数据策略：

- 趋势图、风险分布、成功率等增强型模块允许先使用占位数据
- 但组件结构、视觉语言和信息层级按真实产品设计

### 5. Repository Health 仓库健康列表

作用：把组织级风险状态映射到具体资产。

每项至少包括：

- repository 名称
- 最近一次 review 时间或状态
- open findings 数量
- 接入状态

设计要求：

- 强调“哪些仓库值得优先关注”
- 列表项要兼顾扫读效率与可点击性
- 不做过度复杂的表格，优先做高可读的紧凑列表

## 视觉设计方向

视觉关键词：`polished`、`layered`、`confident`、`operator-grade`

具体方向：

- 采用浅色主基调，不做纯深色监控台
- 使用柔和冷色系表面、渐变背景和层叠式卡片建立高级产品感
- 通过卡片尺寸、留白和布局比例建立主次，不做平均铺满
- 标题排版需要更有产品质感，正文保持工程可读性
- 成功、运行中、风险、失败状态都要有明确但克制的视觉表达

交互细节：

- 卡片 hover 轻微抬升
- action card 有清晰点击反馈
- status chip 支持快速扫读
- recent runs 与 repository list 的行项目支持直接进入后续页面

## 数据策略

本次实现采用“结构优先”策略，按两层数据能力组织：

### 第一层：优先接真实数据

- 当前用户
- 当前组织标识
- 基础 repository 数量
- review runs 基础列表或数量

### 第二层：允许先用占位数据

- 成功率
- 风险分布
- 趋势图
- 仓库健康评分类信息

这样可以保证首页先具备完整产品体验，同时不给当前后端能力施加不必要耦合压力。

## 组件拆分建议

建议把首页拆为以下独立模块：

- `DashboardHero`
- `DashboardKpiGrid`
- `DashboardQuickActions`
- `RecentReviewRuns`
- `RiskInsights`
- `RepositoryHealthList`

拆分原则：

- 每个模块只负责单一展示职责
- 页面容器只负责组织布局与数据拼装
- 避免把所有布局、状态和占位逻辑继续堆在首页单文件中

## 空状态与异常处理

首页必须支持优雅降级，不假设所有数据始终存在。

空状态要求：

- 未接入仓库时，明确引导 `Connect Repository`
- 没有 review runs 时，明确引导 `Start your first review`
- 模块没有增强数据时，显示自然的占位态，而不是空白区域

异常处理要求：

- 如果组织上下文缺失，显示可恢复提示，不直接暴露底层异常
- 如果某一模块数据拉取失败，模块级降级展示，不让整个首页不可用
- 保持项目现有日志与错误处理规范，不使用 `console`

## 响应式策略

- 桌面端保留明显的三层信息层级与主次布局
- 移动端改为单列堆叠
- 模块顺序保持一致：`Hero` → `Quick Actions` → `Recent Runs` → `Insights` → `Repository Health`
- 保证移动端仍然先看到状态总览和关键入口

## 范围边界

本次设计只覆盖登录后 dashboard 首页，不包含以下内容：

- 新的营销官网
- review run 详情页
- repository 管理页
- 图表背后的完整分析系统
- 所有统计指标的一次性真实化接入

## 验收标准

当页面实现完成时，应满足以下结果：

- 登录后首页由简单欢迎页升级为组织级 dashboard
- 页面同时具备总览、动作入口、工作续接和风险洞察四类价值
- 桌面和移动端都能稳定展示核心信息结构
- 页面允许部分占位数据，但整体观感应像真实 SaaS 产品而不是半成品线框
- 首页代码结构按模块拆分，避免单文件继续膨胀
