# 基于 CodeRabbit 调研的竞品产品需求文档（重构版）

## 1. 结论先行

基于现有调研，CodeRabbit 的真正优势不是单点的 AI 审查，而是把 PR 审查、规则配置、自动修复、需求转计划、知识沉淀和团队治理串成一个研发闭环。

但如果我们直接做一个“功能表更满”的对标产品，首版很容易失焦，既做不出明显优势，也做不出可验证的商业价值。

因此，产品首阶段不应追求完整闭环，而应聚焦一个更容易建立信任和付费理由的切入口：

> 一个更强调低噪声、可配置、中英西多语言协作友好，并且能直接给出可交给 AI Agent 执行修复建议的 PR 审查平台。

第一阶段的核心不是“替代所有研发协同能力”，而是先把以下主链路打透：

1. 接入仓库
2. 自动审查 PR
3. 控制评论噪声
4. 结合团队规则给出高价值建议
5. 输出可直接复制给 Agent 的修复提示词
6. 让团队快速感受到 review 成本下降和修复效率提升

对应策略如下：

- **P0 必须聚焦**：`接入 -> 审查 -> 低噪声 -> 规则 -> Agent 修复建议`
- **P1 再补闭环**：一键修复、IDE、CLI、需求转计划、知识库、反馈学习
- **P2 做企业扩展**：私有化、模型路由、治理报表、多仓上下文、成本控制

## 2. 竞品拆解与机会判断

### 2.1 竞品能力对比

| 维度 | CodeRabbit | Greptile | Qodo | Cursor / Bugbot | SonarQube / Codacy | 我们的机会 |
| --- | --- | --- | --- | --- | --- | --- |
| PR 自动审查 | 强，平台级集成成熟 | 强，偏漏洞与深度理解 | 中，偏 IDE 辅助 | 弱，偏编辑器侧 | 中，规则扫描为主 | 做到“低噪声 AI 审查 + 团队规则 + Agent 修复建议” |
| 平台接入 | GitHub / GitLab 成熟 | 中 | 中 | 弱 | 中 | 补齐 `Gitee`，强化国内团队接入 |
| 自动修复 | 有 | 弱 | 弱 | 借助编辑器 | 弱 | 首阶段先做“可复制给 Agent 的修复建议”，再做一键修复 |
| 规则能力 | 有，但门槛偏高 | 中 | 中 | 弱 | 强 | 做最小可用规则配置，降低团队落地门槛 |
| IDE / CLI | 强 | 弱 | 强 | 强 | 弱 | 作为第二阶段增强能力 |
| 需求转计划 | 强，差异化明显 | 弱 | 弱 | 弱 | 无 | 作为第二阶段差异化模块 |
| 企业治理 | 中 | 中 | 中 | 弱 | 强 | 在后续版本补齐治理与部署能力 |
| 多语言协作体验 | 一般 | 一般 | 一般 | 一般 | 一般 | 做中英西三语审查、提示词和规则说明 |

### 2.2 CodeRabbit 值得学习的点

- **完整闭环**：从问题发现到修复落地的链路完整
- **上下文意识**：不仅看 diff，还会结合仓库上下文和历史反馈
- **交付导向**：建议尽量可执行，而不是停留在“指出问题”
- **平台成熟度高**：接入和使用体验相对成熟

### 2.3 CodeRabbit 的可攻击点

- **噪声问题仍明显**：评论价值不均，人工仍需二次筛选
- **对私有代码的顾虑存在**：云端分析对部分团队仍有阻力
- **规则可解释性仍不够强**：很多团队难以知道评论为什么出现
- **本地和企业流程适配存在限制**：对部分组织流程不够贴合
- **成本较高**：按席位扩容时阻力明显

### 2.4 我们的产品策略判断

| 策略类别 | 建议 | 原因 |
| --- | --- | --- |
| 首版切入口 | 聚焦 PR 审查 | 使用频次最高，最容易证明价值 |
| 核心差异化 | 低噪声 + 规则 + Agent 修复建议 | 更容易建立信任，也更容易落地 |
| 必须补齐 | `GitHub / GitLab / Gitee` 接入 | 面向国内团队时，`Gitee` 是必要能力 |
| 暂缓能力 | 一键修复、IDE、CLI、需求转计划 | 对首版价值有帮助，但不是最短成交路径 |
| 后续扩展 | 知识库、治理、私有化、模型路由 | 属于规模化阶段能力 |

## 3. 产品定位

### 3.1 产品定位

面向中大型研发团队、国内协作型技术团队以及存在跨语言协作需求的团队的 AI PR 审查平台，帮助团队在代码合入前更早发现高价值问题、减少低质量评论，并把团队规范沉淀成可持续复用的审查规则。

### 3.2 第一阶段产品定义

第一阶段不是完整研发协同平台，而是一个：

> 低噪声、可配置、支持中英西三语输出、可输出 Agent 修复提示词的 PR 审查产品。

这一定义有三个好处：

- **价值明确**：减少 reviewer 的机械劳动
- **边界清楚**：先解决 PR 场景，不同时做本地、计划、治理全家桶
- **实现可控**：可以在较短周期内做出可试点、可付费的版本

### 3.3 目标用户

- **一线开发者**：希望在 PR 阶段获得可信、可执行、低打扰的反馈
- **Reviewer / Tech Lead**：希望减少机械 review，把精力放在架构和业务判断
- **平台工程团队**：希望通过规则配置把团队规范前置
- **研发管理者**：希望看到 AI 审查是否真正减少 review 成本并提升采纳率

### 3.4 核心价值主张

1. **更少无效评论**：默认只展示高价值问题，减少审查疲劳  
2. **更强团队适配**：通过最小可用规则把团队规范纳入审查上下文  
3. **更快进入修复**：问题可直接转换为可复制给 Agent 的修复提示词  
4. **更适合多语言团队**：支持中文、英文、西班牙语评论、规则说明和修复建议  
5. **更易接入国内环境**：覆盖 `GitHub / GitLab / Gitee` 三类主流仓库场景

### 3.5 产品原则

- **低噪声优先于高覆盖**
- **可执行优先于会表达**
- **规则约束优先于纯模型猜测**
- **模型接入统一优先于多处散接**
- **先打透 PR 主场景，再扩展本地与计划能力**
- **先做最小可用配置，再做平台级复杂治理**

## 4. 产品目标与成功指标

### 4.1 北极星指标

- 月度“有效审查建议采纳数 / 活跃开发者”

### 4.2 第一阶段一级业务指标

- PR 审查覆盖率 >= 60%
- 建议采纳率 >= 35%
- 审查误报率 <= 20%
- PR 平均首轮反馈时长 <= 5 分钟
- 高价值评论占比 >= 70%
- 规则配置启用仓库占比 >= 40%
- Agent 修复提示词被复制或触发使用的比例 >= 25%

### 4.3 第一阶段体验指标

- 新仓库接入后 10 分钟内完成首条审查结果输出
- 增量提交重复评论率 < 10%
- 修复提示词可直接复制成功率 >= 99%
- 中英西三语模板切换成功率 >= 99%
- 用户对评论“有帮助”标记比例 >= 70%

## 5. 阶段取舍说明

### 5.1 为什么 `Gitee` 必须进入 P0

- 文档的目标市场包含国内研发团队，`Gitee` 是不能回避的平台
- 如果只支持 `GitHub / GitLab`，产品叙事与目标客户会脱节
- `Gitee` 接入能力本身也是对“国内团队友好、跨语言协作可接入”定位的直接支撑

### 5.2 为什么一键修复、IDE、CLI 放到 P1

- **一键修复**：需要 patch 生成、应用、冲突处理、回滚等复杂链路，首版实现成本高
- **IDE / CLI**：属于使用频次高但工程面广的能力，容易拖慢首版交付
- **首版更适合先证明“发现问题 + 给出可执行修复建议”**，而不是一步做到自动改代码

### 5.3 为什么自定义规则要放回 P0

- 低噪声的前提不是模型更强，而是模型知道哪些问题值得说
- 没有规则能力，团队规范无法沉淀，评论会更容易漂移
- 规则也是最基础的治理能力，是从“通用 AI 审查”走向“团队可用产品”的关键

### 5.4 为什么需求转计划放到 P1

- 需求转计划是亮点能力，但不是首个购买理由
- 它的使用频次通常低于 PR 审查，不适合拿来做首版主场景
- 它依赖更完整的知识、模板和协作链路，放到 P1 更稳妥

### 5.5 为什么“Agent 修复建议”适合放到 P0

- 它能补上“发现问题”与“开始修复”之间的断点
- 相比一键修复，信任门槛更低，用户更容易接受
- 相比普通评论，更接近交付结果，能直接借力现有 Agent 生态
- 实现成本和产品价值比更适合首版

### 5.6 为什么多语言支持要进入 P0

- 审查评论和修复提示词既要给人看，也要给 Agent 用，语言不匹配会直接影响采纳率
- 很多团队的代码注释、提交说明、协作文档并不统一，默认只支持单一语言会降低落地效果
- 如果首版就支持中文、英文、西班牙语三种输出，产品更容易覆盖国内团队、外包协作团队和跨区域项目
- 该能力更偏输出层和模板层，投入可控，但对用户感知价值很直接

## 7. 关键模块详细需求

### 7.1 模块一：PR 智能审查引擎（P0）

**目标**：在不增加开发者负担的情况下，稳定发现高价值问题，并显著减少 reviewer 的机械劳动。

**核心能力**

- 解析 PR diff，识别变更文件、函数、依赖关系和关键调用链
- 补充必要上下文：相邻文件、被调用接口、规则配置、历史反馈
- 输出三层结果：PR 摘要、重点问题、修复建议
- 默认只展示高置信度建议，其余建议折叠到次级层
- 支持评论去重、状态追踪和建议关闭原因记录

**产品要求**

- 支持“严格 / 标准 / 宽松”三档审查模式
- 支持“只看 blocker / 只看安全 / 只看可修复”过滤器
- 支持 reviewer 对评论进行确认、忽略、转任务、要求重查
- 支持增量审查场景的旧评论折叠与新评论高亮

**为什么比 CodeRabbit 更好**

- 不追求评论数量，而追求采纳率和信任度
- 把置信度、业务影响、可修复性一起纳入排序
- 通过规则配置减少团队不关心的泛化评论

**验收标准**

- 严重问题识别召回率达到预设基线
- 真实试点团队中，采纳率和人工满意度高于无 AI 对照组
- 重复评论和无效评论占比可被后台监控

### 7.2 模块二：Agent 修复建议（P0）

**目标**：把“发现问题”转化为“可立即交给 AI Agent 执行的修复任务”，缩短从评论到修复的路径。

**典型用户场景**

- 开发者看到一条问题评论，不想手工重新组织上下文给 Agent
- reviewer 希望把问题直接交给编码 Agent 处理，再自己做最终把关
- 团队希望先验证“AI 能否可靠修复问题”，但暂时不接受产品直接改代码

**输入上下文**

- 问题描述与严重级别
- 相关代码片段与变更文件
- 规则命中信息和风险解释
- 可选的仓库约束、编码规范、测试要求

**输出内容**

系统应生成一段可直接复制给 Agent 的结构化提示词，至少包含：

- 问题摘要
- 根因判断
- 影响范围
- 建议修改的文件或模块
- 修改约束
- 验收标准
- 测试建议
- 不确定项和假设

**交互要求**

- 支持按单条评论生成修复提示词
- 支持按多个相关评论合并生成修复提示词
- 支持一键复制
- P0 支持中文、英文、西班牙语三种默认模板
- 支持仓库级默认语言配置和用户临时切换
- 支持针对不同 Agent 预留模板差异化能力，但 P0 可先统一模板

**输出示意结构**

```md
目标：修复以下 PR 中的问题，并保持现有行为不回归。

问题摘要：
- ...

根因判断：
- ...

需要修改的文件：
- ...

修改约束：
- 不改变现有对外接口
- 保持兼容当前单元测试

验收标准：
- ...

测试建议：
- ...

如果信息不足，请先说明你的假设，再给出修改方案。
```

**为什么比 CodeRabbit 更好**

- 更强调中英西三语协作和执行导向，适合直接贴给团队常用 Agent
- 更强调结构化输出，而不是一段泛化解释
- 可与团队规则联动，让提示词更贴近真实开发约束

**验收标准**

- 用户可在问题详情中一键复制修复提示词
- 提示词复制后可在主流 Agent 产品中直接使用
- 试点团队中，使用修复提示词的问题处理时长明显短于纯手工修复路径

### 7.3 模块三：最小可用自定义规则（P0）

**目标**：让团队把最基础的工程规范纳入审查上下文，降低误报和无关评论比例。

**P0 范围**

- 仓库级 YAML 配置
- 忽略目录 / 文件类型
- 审查严格度配置
- 评论展示阈值配置
- 少量规则模板，如命名规范、禁止修改目录、接口兼容提醒

**明确不在 P0 的内容**

- 完整可视化规则中心
- 组织、项目、目录三级继承
- 命中分析大盘
- 模板市场
- 仅观测不拦截等复杂策略

**产品要求**

- 支持在仓库根目录放置规则文件
- 支持规则校验和错误提示
- 支持查看某条评论受到了哪些规则影响
- 支持默认模板快速生成基础配置

**为什么比 CodeRabbit 更好**

- 强调最小可用，而不是把规则能力做成平台工程专属能力
- 让团队在低门槛下就能获得更低噪声的审查结果

**验收标准**

- 新规则可在下一次 PR 审查中稳定生效
- 团队能理解评论与规则之间的关系
- 配置错误时系统能给出明确提示

### 7.4 模块四：基础安全审查（P0）

**目标**：在通用代码审查之外，优先识别常见高风险安全问题。

**核心能力**

- 支持基础安全规则和漏洞模式识别
- 安全问题默认进入高优先级评论集合
- 输出问题影响、风险等级和修复方向
- 可与 Agent 修复建议联动生成安全修复提示词

**产品要求**

- 首版覆盖高频风险类型
- 安全评论与普通质量评论在视图中区分展示
- 安全问题默认不被低噪声模式完全折叠

**验收标准**

- 常见漏洞样例可稳定命中
- 安全问题解释清晰，不只给结论

### 7.5 模块五：多语言输出（P0）

**目标**：让审查结果和修复提示词可以在不同协作语言下保持一致理解，降低沟通损耗并提升 Agent 可用性。

**P0 范围**

- 支持中文、英文、西班牙语三种输出语言
- 覆盖 PR 摘要、逐条评论、规则说明、Agent 修复提示词
- 支持仓库级默认语言配置
- 支持用户在界面中临时切换输出语言

**产品要求**

- 语言切换只影响展示和提示词输出，不改变底层问题识别结果
- 同一条问题在三种语言下的严重级别、修复方向和约束信息应保持一致
- 如果某个术语无法自然翻译，应优先保留代码术语并补充简短解释
- 多语言输出需与规则系统联动，避免规则名称和提示词内容脱节

**为什么放在 P0**

- 这是高感知、低阻力的体验能力，能直接提升评论可读性和 Agent 使用成功率
- 与 Agent 修复建议强相关，越早做越容易形成统一模板

**验收标准**

- 用户可在同一问题上切换中英西三种语言输出
- 三种语言下的核心语义一致，不出现明显信息缺失
- 试点团队中，多语言切换后的评论理解成本显著下降

### 7.6 模块六：一键修复（P1）

**目标**：在 Agent 修复建议被验证有效后，进一步缩短从建议到代码落地的路径。

**核心能力**

- 支持单条修复和批量修复
- 支持 patch 预览、应用和回滚
- 支持 patch 应用失败时给出明确错误

**阶段关系**

- P0 先验证“修复建议是否被团队接受”
- P1 再验证“产品是否可以自动交付 patch”

### 7.7 模块七：IDE / CLI 本地审查（P1）

**目标**：把问题发现时间从 PR 后前移到编码阶段。

**核心能力**

- VS Code 插件支持未提交改动的快速审查
- CLI 支持 `staged`、`branch diff`、`commit range`
- 可输出机器可读 JSON，便于接入 CI

**阶段原因**

- 该能力价值高，但工程面更广，不适合作为首版阻塞项

### 7.8 模块八：需求转计划（P1）

**目标**：把模糊需求转成开发团队和 AI Agent 都可执行的计划。

**核心能力**

- 输入支持 Issue、PRD、自由文本、会议纪要
- 输出背景理解、目标边界、阶段任务、风险清单、验收标准
- 支持导出为 Markdown、Issue comment、Agent prompt

**阶段原因**

- 属于高差异化能力，但不是首版最短价值链路
- 需要在审查、规则、知识基础打稳后再放大价值

### 7.9 模块九：知识库与治理能力（P1 / P2）

**目标**：让团队知识、权限策略和部署方式逐步成为产品护城河。

**核心方向**

- 知识库与反馈学习
- RBAC、审计日志、模型权限控制
- SaaS / VPC / 私有化部署
- 模型调用成本统计和配额控制

## 8. 用户旅程设计

### 8.1 第一阶段开发者旅程

1. 接入 `GitHub / GitLab / Gitee` 仓库  
2. 提交 PR 后自动获得摘要与重点问题，并可按中 / 英 / 西切换输出  
3. 只查看高价值评论，减少噪声干扰  
4. 对单条问题生成 Agent 修复建议并直接复制使用  
5. 修复后再次 push，由增量审查确认问题是否解决  
6. 团队通过规则文件持续优化评论质量

### 8.2 第一阶段管理者旅程

1. 接入核心仓库
2. 配置基础规则和审查严格度
3. 查看采纳率、误报率和规则使用情况
4. 找到高噪声仓库并持续调优

### 8.3 产品关键时刻

- 第一次接入后 10 分钟内出现可用审查结果
- 第一次 PR 审查中发现至少 1 条团队认可的高价值问题
- 第一次规则配置生效并明显减少无关评论
- 第一次 Agent 修复提示词被直接复制并成功用于修复
- 第一次中 / 英 / 西语言切换后，评论与提示词仍保持一致可用

## 9. 非功能需求

### 9.1 性能

- PR 首轮分析：常规 30 文件以内在 5 分钟内完成
- 增量提交分析：60 秒内完成
- 修复提示词生成：10 秒内完成
- 首次接入向导：10 分钟内完成配置

### 9.2 安全

- 全链路 TLS 加密
- 代码与审查数据按租户隔离
- 支持代码零保留或按策略保留
- 模型统一通过 `Vercel AI SDK` 接入，不在业务代码中分散直连各家模型 SDK
- 模型提供商 API Key 存放在数据库中并加密管理，不以下明文方式落库，不下发前端
- 敏感仓库后续支持指定部署模式和模型策略

### 9.3 稳定性

- 核心审查服务可用性目标 >= 99.9%
- 模型超时支持自动降级到备用模型或规则模式
- 审查失败不阻塞 PR 正常流程，但应给出清晰提示

### 9.4 可观测性

- 可追踪审查耗时、模型耗时、规则命中、采纳率、误报反馈
- 可追踪 Agent 修复提示词的生成、复制和后续使用情况
- 可按仓库、语言、团队查看效果

## 10. MVP 范围建议

### 10.1 第一阶段 MVP

聚焦“替代人工审查中的 30% 机械工作”，而不是一开始追求完整研发协同平台。

**MVP 必做**

- `GitHub / GitLab / Gitee` 接入
- PR 自动审查
- 增量审查
- 低噪声排序与去重
- Agent 修复建议
- 中 / 英 / 西三语输出
- 仓库级 YAML 规则配置
- 基础安全审查
- 基于 `Vercel AI SDK` 的统一模型接入层

**MVP 不做**

- 一键修复
- IDE 本地审查
- CLI 审查
- 需求转计划
- 大而全知识库
- 私有化部署
- 多仓高级图谱
- 大而全 BI 看板

### 10.2 第二阶段

- 一键修复
- IDE 本地审查
- CLI 审查
- 需求转计划
- 计划协同与版本对比
- 知识库
- 反馈学习
- 协作通知与任务同步
- 基础权限与审计

### 10.3 第三阶段

- 私有化部署
- 多仓上下文
- 模型路由
- 管理驾驶舱
- 成本治理与 SLA

## 11. 商业化建议

### 11.1 定价思路

建议采用混合定价，而不是单一按人头收费：

- 免费版：开源仓库 / 小团队 / 基础 PR 审查
- 团队版：按活跃开发者 + 仓库数
- 增强包：Agent 修复增强、规则模板、更多安全能力
- 企业版：按部署形态、仓库规模、合规模块收费

### 11.2 更适合拿下的客户类型

- 已有明确 PR review 压力，希望先降本增效的研发团队
- 使用 `GitLab` 或 `Gitee`，希望补齐 AI 审查能力的国内组织
- 存在中英西跨语言协作需求的项目团队
- 对 CodeRabbit 感兴趣，但担心噪声、规则适配和价格的团队

## 12. 风险与缓解

| 风险 | 表现 | 缓解建议 |
| --- | --- | --- |
| 审查误报高 | 开发者快速失去信任 | 默认高置信度模式 + 规则约束 + 反馈闭环 |
| 规则配置门槛高 | 团队不会配、不愿配 | 先做最小可用 YAML + 默认模板 |
| Agent 修复建议不够可执行 | 用户复制后仍需大量手工补充 | 强制输出结构化字段，先围绕高频问题打磨模板 |
| 多语言输出质量不一致 | 不同语言下理解偏差，影响信任 | 对中英西三语建立统一术语表和模板回归测试 |
| P0 范围再次膨胀 | 交付节奏失控 | 严控首版只做 PR 主链路，不提前做 IDE/CLI/计划 |
| 国内平台适配不足 | 目标用户不认可定位 | `Gitee` 在首版即进入正式支持范围 |

## 13. 最终建议

如果目标是做一个能真正替代 CodeRabbit 的产品，最重要的不是功能更多，而是先建立三个替代理由：

1. **更可信**：低噪声、规则可解释、评论更贴近团队约束  
2. **更易落地**：问题可以直接转成可交给 Agent 的修复任务  
3. **更适合协作团队**：支持 `Gitee`、中英西三语输出和渐进式接入

一句话版本：

> 用“低噪声 PR 审查 + 最小可用规则 + Agent 修复建议”切入市场，再逐步扩展到自动修复、本地审查、需求转计划和企业治理，而不是首版就做一个过重的全链路平台。
