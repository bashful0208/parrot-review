# P0 数据库设计评审意见

## 1. 评审结论

本次 P0 数据库设计在主键与审计字段策略上，建议采用“工程统一优先”的统一规范：除极特殊情况外，所有业务表统一保留 `id`、`created_at`、`updated_at`。即使个别表从纯范式角度看可以进一步收缩，也建议在 P0 阶段继续保留，避免过早做结构特化。

## 2. 总体评审结论

- 当前方案整体合理，已基本符合统一主键与时间字段规范
- 统一使用 `UUID id + created_at + updated_at`，对多租户、异步任务、增量审查、问题状态流转等场景是合适的
- 从数据库极简角度，少数表存在“可不保留全部通用字段”的讨论空间
- 但从当前产品阶段、工程复杂度、未来演进成本来看，不建议为少数表单独做例外设计
- 评审建议为：`P0 所有业务表统一保留 id / created_at / updated_at`

## 3. 采用统一通用字段的理由

- 统一接口模型，降低前后端、ORM、管理后台、审计系统的处理复杂度
- 统一支持记录定位、单条引用、事件排查、数据修复、后台操作
- 统一支持按创建时间排序、分页、统计、归档
- 统一支持后续软删除、归档、同步、重放、幂等修复等能力扩展
- 避免现在为“少数字段优化”做特化，后续又因业务增长补回字段，产生二次迁移成本

## 4. 逐表评审意见

### `organizations`

结论：必须保留
说明：组织是多租户根实体，必须支持独立引用、更新、排序、审计。
建议：`status`、`plan_tier` 后续可进一步收敛为受控枚举或受限字典值。

### `memberships`

结论：必须保留
说明：该表虽然表现为“组织-用户关系”，但包含 `role`、`status`、`invited_by`、`joined_at` 等业务语义，属于独立关系实体，不应按纯 join table 对待。
建议：如后续引入邀请流程，建议补充 `invited_at`，使邀请时间与加入时间语义更清晰。

### `repositories`

结论：必须保留
说明：仓库是核心业务对象，需要被配置、规则、PR、运行记录等大量实体引用。
建议：可进一步核查仓库唯一性语义是否足够清晰，避免重复接入同一平台仓库。

### `repo_integrations`

结论：必须保留
说明：该表承载接入配置、授权信息、状态与扩展元数据，属于独立配置实体。
建议：`status` 建议后续收敛为枚举；若未来限制同仓库同平台仅允许唯一有效接入，可考虑补充更严格约束。

### `webhook_events`

结论：必须保留
说明：该表是事件流水与幂等处理基础表，需要支持追踪、排错、状态更新、重试分析。
建议：

- 若平台侧 `delivery_id` 稳定存在，可考虑改为 `not null`
- 需明确 `updated_at` 表示处理状态变化时间，不等同于业务事件发生时间

### `pull_requests`

结论：必须保留
说明：PR 是核心业务实体，必须具备独立主键与完整时间审计字段。
建议：继续保留 `opened_at`、`closed_at`、`merged_at` 与通用时间字段并存，这种设计是合理的。

### `pr_commits`

结论：必须保留
说明：虽然可通过 `(pull_request_id, commit_sha)` 形成业务唯一性，但工程上仍建议保留独立 `id`，便于引用、排查和后续扩展。
建议：该表业务上应尽量少更新，保持提交快照属性。

### `rule_sets`

结论：必须保留
说明：规则集是独立管理对象，存在启停、版本切换、应用时间等状态，必须保留完整通用字段。
建议：若业务规则明确，可增加“同仓库同来源仅一个活跃规则集”的约束。

### `rule_versions`

结论：必须保留
说明：规则版本会被当前生效版本引用，本身就是独立版本实体，不适合压缩成无主键明细。
建议：业务层应尽量保证版本发布后不可变，减少对历史版本记录的更新。

### `ai_provider_configs`

结论：必须保留
说明：模型配置是独立配置实体，需要审计、启停、引用和后续轮换。
建议：需提前考虑停用配置后是否允许重建同名配置，避免唯一性策略与运营动作冲突。

### `ai_provider_bindings`

结论：必须保留
说明：该表并非纯映射表，还包含任务类型、优先级、启用状态、回退配置等业务语义。
建议：建议补充优先级排序规则说明，例如“数值越小优先级越高”。

### `review_runs`

结论：必须保留
说明：该表是审查链路核心聚合实体，必须具备独立主键、完整生命周期字段与更新时间。
建议：继续明确区分 `created_at`、`started_at`、`finished_at` 三者语义，避免统计时混用。

### `changed_files`

结论：建议保留
说明：从极简设计看，这张表可被理解为某次运行下的文件明细；但按工程统一原则，仍建议保留 `id + created_at + updated_at`，便于快照引用、后台排查和后续扩展。
建议：当前唯一约束 `unique (review_run_id, file_path, previous_path)` 需重点复核 `null` 语义，避免在 `previous_path is null` 时出现重复记录漏洞。

### `review_issues`

结论：必须保留
说明：问题记录是核心业务实体，涉及状态流转、跨 run 去重、忽略、确认、解决等操作，必须保留完整通用字段。
建议：若后续要强化“跨 run 生命周期”，可再演进为“问题主实体 + 命中明细”双层模型，P0 阶段先保持当前结构即可。

### `review_comments`

结论：必须保留
说明：评论需要草稿、发布、失败、隐藏、同步等状态管理，是独立对象而非 issue 附属字段。
建议：如后续支持线程回复，可预留 `parent_comment_id` 一类结构。

### `review_feedback`

结论：建议保留
说明：从范式角度，这张表可被视为“用户对问题的反馈关系”；但由于它带有 `feedback_type`、`reason`、`review_run_id` 等业务属性，按工程统一原则仍建议保留完整通用字段。
建议：当前 `unique (review_issue_id, user_id)` 表示单用户对单问题仅保留一条当前反馈，逻辑合理；若未来要保留反馈历史，需调整为事件流模型。

### `agent_prompts`

结论：必须保留
说明：该表是独立产物实体，涉及生成、复制、统计、追踪，应保留完整通用字段。
建议：`source_issue_ids uuid[]` 在 P0 可接受；若后续需要更强检索和关联能力，可演进为中间关系表。

### `usage_events`

结论：建议保留
说明：从“事件表应 append-only”的角度，`updated_at` 使用频率可能较低；但从工程一致性、排查和补偿处理考虑，仍建议保留。
建议：

- 业务层尽量采用只插入少更新的策略
- 保持 `occurred_at` 与 `created_at` 并存，分别表示业务发生时间与入库时间

## 5. 可保留但不建议现在裁剪的表

以下表从“数据库极简”角度有讨论空间，但本次评审建议继续保留 `id / created_at / updated_at`：

- `memberships`
- `pr_commits`
- `changed_files`
- `review_feedback`
- `usage_events`

原因：

- 这些表都不是纯粹无状态关系表
- 都存在独立查询、排障、审计、后台处理或未来扩展需求
- 当前阶段统一结构收益高于局部特化收益

## 6. 重点优化建议

- 优先复核 `changed_files` 的唯一约束设计，特别是 `previous_path` 为 `null` 时的重复记录风险
- 为所有 `text` 类型状态字段补充清晰的允许值约束文档，避免后续脏数据
- 对偏历史/事件属性的表，虽然保留 `updated_at`，但业务实现上应尽量少更新、保持记录稳定
- 在设计文档中明确：通用字段统一保留是一项“工程规范决定”，不是逐表临时判断结果

## 7. 最终评审结论

建议通过当前主键与时间字段设计方案，并明确落地以下统一规范：

- 所有业务表统一保留 `id uuid primary key`
- 所有业务表统一保留 `created_at timestamptz not null default now()`
- 所有业务表统一保留 `updated_at timestamptz not null default now()`
- 通过统一 `set_updated_at` trigger 维护更新时间
- P0 阶段不对少数表做字段裁剪特化，后续如有明确性能或存储压力，再针对个别 append-only 表单独评估
